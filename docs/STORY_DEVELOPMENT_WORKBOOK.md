# 내 이야기 개발 워크북

이 문서는 실제 원문을 기반으로 사용자와 에이전트가 채울 작업 양식이다. 빈칸은 미정이며 가상의 사용자 작품으로 채우지 않는다. 다섯 작업 구간과 세부 Target은 [정밀 작업 명세](STAGE_EXECUTION_SPEC.md)에 있다. **새 CLI·schema·자동 저장 기능이 아니다.**

세부 판단과 실패 복구는 [정밀 작업 명세](STAGE_EXECUTION_SPEC.md)와 그 문서가 연결하는 연구 메모를 사용한다. 문서의 기록용 필드를 기존 제품 API의 새 필드로 임의 제출하지 않는다.

원고를 지정하면 사본을 해당 작품의 작업 공간에 두고 작성한다. 이 저장소의 양식 자체를 작품의 정본으로 사용하지 않는다. geultu와 NVC에 내용을 채택할 때는 기존 공개 명령과 검토 절차를 사용한다. 이 양식의 ‘채택’ 메모가 제품의 승인 기록을 대신하지 않는다.

## 1. 작품의 출발점

- 작품명 또는 임시 제목:
- 사용자가 지정한 원문 경로·revision/hash:
- 입력 상태: 메모 / 일부 원고 / 완성 원고 / 기타
- 먼저 완성할 결과: 읽는 스토리 / 대본·텍스트 콘티 / 매체별 각색 문서
- 독자·관객:
- 장르·톤·목표 분량:
- 이번에 고칠 범위:

에이전트는 원문을 먼저 읽고 이미 답이 있는 항목을 작성한다. 결말·인물 정체·핵심 관계처럼 의미를 바꾸는 미결 사항만 질문한다. 원문의 의도적인 모호함을 결함으로 단정하지 않는다.

## 2. 내가 지키고 싶은 이야기

- 이 이야기를 쓰는 이유:
- 마지막에 남기고 싶은 감정·질문:
- 반드시 살릴 장면·대사·이미지:
- 바꾸지 않을 결말·관계·설정:
- 바꿔도 되는 표현·순서·세부:
- 피하고 싶은 전개·말투:

| 보호 항목 | 원문 근거 또는 사용자의 명시적 선택 | 보호하는 이유·기능 | 의미 변경 시 필요한 판단 |
|---|---|---|---|
|  |  |  |  |

근거를 적을 때 사실, 인물의 믿음, 해석, 에이전트의 제안을 표시한다. 원문에 없는 설정을 ‘원래 설정’으로 기록하지 않는다.

## 3. 이야기의 중심

- 한 문장 로그라인:
- 주인공이 원하는 것:
- 그것을 막는 사람·상황·내적 모순:
- 실패할 때 잃는 것:
- 끝에서 해야 하는 선택:
- 그 선택이 처음의 주인공에게 어려운 이유:

방향이 실제로 갈릴 때만 다음 표를 사용한다. 사소한 표현 차이를 선택지로 부풀리지 않는다.

| 발전 방향 | 살리는 원문 요소 | 바뀌는 의미·추가하는 것 | 기대 효과·잃는 것 | 선택 상태 |
|---|---|---|---|---|
|  |  |  |  | 제안 |

## 4. 인물과 관계의 집필용 가설

| 인물 | 욕망·두려움 | 스스로 믿는 것 | 행동으로 드러나는 모순 | 관계의 시작 → 끝 | 원문 근거·미정 |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

이 표는 스토리를 발전시키기 위한 노트다. NVC의 승인된 인물 상태를 직접 수정하지 않는다. 관계 변화에는 그것을 일으키는 구체적인 사건·선택이 있어야 한다.

## 5. 사건의 연결과 감정 흐름

| 사건·작업 ID | 앞선 원인 | 인물의 선택·행동 | 결과와 다음 압력 | 새로 알게 되는 것 | 독자의 감정·질문 | 복선·회수·근거 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

정해진 사건 수나 3막 비율을 채우는 것이 목적이 아니다. “그다음에”로만 연결되는 사건을 찾아 “그 선택 때문에”라는 인과가 필요한지 판단한다. 의도적인 우연·생략·열린 결말은 그 기능을 설명하고 유지할 수 있다.

## 6. 글투와 실제 본문

- 원문에서 관찰한 시점·서술 거리:
- 리듬·반복·생략·어휘의 구체적 예:
- 인물별 높임말·호칭·대화 습관:
- 유지할 표현과 과장하지 말아야 할 표현:
- 필요한 경우에만 작성하는 시험 문단:

이후 실제 스토리 본문을 구간별로 작성한다. 요약·분석·작성 예정 안내를 완성 본문으로 제출하지 않는다. 현재 geultu 제출에서는 `blocks`, `change_summary`, `assumptions`, `open_questions`의 기존 계약을 따른다. 이 워크북의 표를 새 필드로 임의 제출하지 않는다.

## 7. 퇴고 요청 카드

- 대상 문서·revision·block 또는 scene ID:
- 관측된 문제와 본문 근거:
- 원하는 독자 경험:
- 보존할 의미·사용자의 직접 수정:
- 이번 수정: 표현 / 호흡·순서 / 장면 구성 / 서사 변경 제안
- 영향을 받을 다른 부분과 그 근거:
- 수정 전·후 실제 본문:
- 아직 판단이 필요한 점:

표현을 다듬는 요청에서 새 범인·새 능력·새 결말을 몰래 추가하지 않는다. 삭제·병합으로 사라지는 정보·감정·복선의 기능을 확인한다. 구조 문제를 고치는 데 더 넓은 변경이 필요하면 실제 변경 후보와 범위를 제시한다.

## 8. 시놉시스 압축 보존표

| 원문·스토리의 중요한 요소 | 시놉시스의 대응 위치 | 유지 / 압축 / 재배열 / 생략 / 미정 | 이유 | 후속 각색에 꼭 전달할 조건 |
|---|---|---|---|---|
|  |  |  |  |  |

제작 시놉시스에는 결말을 포함한다. 홍보 소개문은 별도 결과물이다. 보호한 관계·반전·결말의 누락이 있으면 시놉시스를 수정하거나 사용자의 변경 결정을 받는다.

**현재 인계의 한계:** `authoring.handoff`는 채택한 시놉시스만 인계한다. 이 표·글투·보호 조건을 자동 전달한다고 가정하지 않는다. 현재 사용에서는 시놉시스에 필요한 핵심 조건이 실제로 반영됐는지 검토하고, 별도 reference를 사용할 경우 NVC가 허용하는 공개 입력 경로를 확인한다. 완전한 companion 인계는 리뉴얼의 후속 구현이다.

## 9. 씬 카드와 대본

NVC 작업은 `next`가 반환하는 실제 packet·task token에 맞춘다. 다음 항목은 기존 STS scene blueprint를 읽기 쉽게 검토하는 질문이다.

- 이 장면이 꼭 해야 하는 일은 무엇인가.
- 시작할 때 각 인물은 어디에 있고 무엇을 알고 믿는가.
- 지금 원하는 것은 무엇이며 무엇이 막는가.
- 인물이 실제로 어떤 행동·선택을 하는가.
- 장면 중 무엇이 뒤집히거나 달라지는가.
- 끝에서 관계·지식·소품·위치·목표가 어떻게 변하는가.
- 그 변화 때문에 다음 장면에서 가능한 일은 무엇인가.
- 대사로 설명하는 대신 행동·소리·공간으로 보여줄 부분이 있는가.
- 보호한 원문 요소가 어떤 행동·대사·표현으로 살아 있는가.

대본을 쓴 뒤에는 인과·인물 상태·연속성·대사의 의도·말하지 않은 뜻을 검토한다. 역복원 검토는 대본만 제공받는 별도의 입력 맥락에서 수행해야 한다. 같은 대화에서 원문을 본 뒤 ‘못 본 척’한 검토를 독립 검증으로 기록하지 않는다. 기존 STS 검토와 최종 Human release를 따른다.

## 10. 텍스트 콘티

| 현재 씬·semantic occurrence 참조 | 패널의 목적 | 구도 | 동선·시선 | 원 씬의 행동·대사 | 소리·전환 | 검토 사항 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

참조 ID와 hash는 실제 NVC packet에서 가져온다. 콘티에서 새 사건·대사를 만든 경우 씬의 의미가 바뀌므로 앞 단계의 수정 후보로 돌린다. 실제 제출은 NVC `draftSchema`를 따르며 위 표는 검토용이다. 모든 씬·occurrence의 요구 coverage와 별도 review를 확인한다.

## 11. 판본 출고 메모

- 사용자가 검토한 실제 판본과 hash:
- 이번 결과물의 범위:
- 패키지에 들어갈 실제 문서:
- 마지막으로 남은 미정·제외 사항:
- 다음 판본에서 고칠 것:
- 실제 export/package 경로와 결과 상태:

현재 전체 package에는 원문·스토리·시놉시스·씬 설계·대본·씬 맵·텍스트 콘티와 검토 기록이 들어간다. 이 워크북은 현재 package가 자동 수집하지 않는다. 결과 파일과 manifest를 확인한 뒤 출고 상태를 기록한다. 실제 영상·이미지가 없는 문서 묶음을 영상·이미지 제작 완료로 표현하지 않는다.
